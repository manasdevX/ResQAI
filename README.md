ResQAI is a full-stack emergency management platform built to coordinate disaster response across four roles — citizens, field responders, shelter managers, and admins — through a single shared real-time interface.

When a disaster strikes, everyone needs different things. Citizens need to get help fast. Responders need to know where to go. Shelter operators need to know how full they are. Admins need to see everything at once. ResQAI gives each of them exactly that, all connected through live WebSocket events so nothing requires a page refresh.

## User Roles

| Role | Gets access to |
|------|----------------|
| **Citizen** | SOS button, incident reporting, shelter finder, resource requests, nearby incident feed |
| **Responder (Volunteer)** | Incident dispatch, assignment management, resource fulfilment, skill profile |
| **Shelter Manager** | Their assigned shelter — occupancy, status, and contacts |
| **Admin** | Everything above, plus analytics, user management, broadcast alerts, and invite system |

**How roles are created:**
- **Citizens** and **Responders** can select their role during standard signup on the site.
- **Shelter Managers** and additional Responders can be invited via a one-time link generated by an Admin.
- **Admins** are created via a database seed script.

## Features

### For Citizens

**SOS Emergency Alert**  
The SOS button is the most prominent thing on the citizen home screen. Tapping it asks for confirmation before doing anything — a deliberate guard against accidental triggers. On confirmation, it grabs the device's GPS coordinates and sends an emergency alert instantly. Every online responder and admin gets notified in seconds. When a responder accepts, the citizen receives a notification telling them who's coming.

**Incident Reporting**  
Citizens can report any emergency — fire, flood, earthquake, medical emergency, building collapse, and more — with a title, description, location, and up to 5 photos or videos. The moment a report is submitted, it appears on the admin live map and in every responder's feed. The citizen can track their report's status (reported → acknowledged → responding → resolved) from their My Reports page and gets notified at each step.

**Shelter Finder**  
The Shelters page shows a Leaflet map alongside a searchable list of registered shelters. Citizens can filter by type (hospital, relief camp, school, etc.), status, and amenities like food, water, medical supplies, or wheelchair accessibility. They can check themselves into a shelter directly from the app — occupancy updates live for everyone. There's also an OSM tab that pulls real hospitals, police stations, fire stations, and pharmacies from OpenStreetMap with no API key needed.

**Resource Requests**  
A single button on the home screen lets citizens request food, water, medical help, clothing, or shelter. The request is pinned to their GPS location so nearby responders can see and fulfil it.

**Mark Yourself Safe**  
After a disaster event, citizens can mark themselves safe from their home screen. It's a small thing but useful for families and coordination teams.

**Nearby Incident Feed**  
The home screen shows a live feed of active incidents within 20 km. Each card includes the incident type, severity badge, location, and the first AI-recommended action — so citizens know what's happening around them.

### For Responders

**Smart Dispatch Notifications**  
When a new incident is reported, the system matches it to responders based on their skill profiles. A fire goes to people with firefighting or rescue skills first. A medical emergency goes to those with first aid or paramedic skills. Matched responders get a notification card on their dashboard with the incident details and AI summary. If nobody with matching skills is available, it goes to all available responders instead.

**Nearby Incidents**  
Responders have a dedicated incidents page showing active incidents near them on a map and in a list, sorted by distance. They can filter by type and severity, view the full AI triage summary, and accept a task directly from the list. Accepting marks them as assigned and notifies the original reporter.

**My Assignments**  
A separate page tracks all incidents a responder is currently assigned to, with status and the ability to move things forward.

**Resource Fulfilment**  
Responders see nearby resource requests from citizens. They can acknowledge a request to claim it, then mark it fulfilled when delivered.

**Skill Profile & Duty Toggle**  
Responders manage a skills list from their dashboard (e.g. "first aid", "search and rescue", "driving"). They also have an ON DUTY / OFF DUTY toggle — when they go on duty, they show up as available for dispatch and the admin's live count updates immediately.

**Auto-Escalation**  
If no responder accepts an incident within 15 minutes, the system automatically alerts all admins so they can intervene manually.

---

### For Shelter Managers

Shelter managers have a focused view scoped entirely to their assigned shelter. From their panel they can:

- Update occupancy numbers and current status (active, full, preparing, closed)
- Edit shelter details — name, address, contacts, amenities
- See who's checked in

Every occupancy change is broadcast live so the Shelters page and admin dashboard always reflect the real number.

---

### For Admins

**Live Incident Map**  
The admin dashboard is a full-screen split view: a live Leaflet map on one side showing every active incident as a colour-coded marker (red for critical, orange for high, yellow for medium, green for low), and a real-time incident feed on the other. New incidents appear on both the moment they're submitted. The feed also shows SOS alerts in a dedicated strip, and escalation banners for incidents that haven't been accepted within 15 minutes.

**Incident Management**  
Clicking any incident opens a management panel where admins can change status, change severity, assign or unassign specific responders, and view the full status history log, attached media, and the AI triage output (summary, risk score, estimated affected count, recommended actions).

**Emergency Broadcast**  
Admins can push a system-wide alert — evacuation, medical, shelter, or general — from the Alerts panel. It fires to every connected user instantly and shows as a banner across all dashboards.

**Shelter Management**  
Admins can create, edit, and delete shelters; set capacity and amenities; update status; and assign a shelter manager to any shelter.

**Analytics Dashboard**  
A data overview of the entire operation: total incidents, active and critical counts, resolution rate, average resolution time, incident breakdown by severity/type/status, a 7-day daily trend chart, shelter utilisation rate, and responder on-duty count. All pulled from a single MongoDB aggregation.

**User Management**  
Search and filter all registered users, change their roles, and activate or deactivate accounts.

**Invite System**  
To onboard a new responder or shelter manager, the admin generates an invite link from the Invites panel. The link expires after 48 hours and can only be used once. The invitee signs up via that URL and gets the correct role automatically.

**AI Triage on Every Incident**  
Every incident reported on the platform is automatically analysed by Gemini 2.0 Flash. The AI produces a severity rating, a 0–100 risk score, an estimated affected count, and a list of recommended actions. This shows up inline on the admin dashboard and in the full incident view — admins don't have to read every report to understand what's urgent.

---

### Shared — Real-Time Chat

All four roles can send direct messages to each other. The chat has:

- **Live presence** — green/grey dots show who's online right now
- **Typing indicators** — you see when the other person is typing
- **Unread badges** — per-conversation unread counts on the sidebar
- **Replies** — reply to a specific message with a quoted preview
- **Message delete** — senders can delete their own messages; admins can delete any
- **Incident threads** — each incident has its own message thread for field updates between assigned responders

Everything is persisted — message history is available as a scrollable log.

## Getting Started

### Prerequisites

- Node.js v18+
- MongoDB (local or [Atlas](https://www.mongodb.com/atlas))
- [Cloudinary](https://cloudinary.com) account — for photo and video uploads
- [Google AI Studio](https://aistudio.google.com) API key — for incident triage
- SMTP credentials — Gmail with an [App Password](https://support.google.com/accounts/answer/185833) works fine

### Setup

```bash
# Clone
git clone https://github.com/your-username/ResQAI.git
cd ResQAI

# Backend
cd backend
npm install
cp .env.example .env    # fill in your values
npm run dev             # starts on http://localhost:5000

# Frontend (new terminal)
cd ../frontend
npm install
cp .env.example .env
npm run dev             # starts on http://localhost:5173
```

### Create the first admin account

```bash
# from backend/
node seeds/createAdmin.js
```

The script prints the login credentials. Use them to log in, then head to the **Invites** panel to onboard your first responders and shelter managers.

## Environment Variables

### `backend/.env`

| Variable | Required | Description |
|----------|:--------:|-------------|
| `MONGO_URI` | ✅ | MongoDB connection string |
| `JWT_SECRET` | ✅ | Signing secret — minimum 32 characters |
| `PORT` | — | Defaults to `5000` |
| `FRONTEND_URL` | — | CORS origin and email link base — defaults to `http://localhost:5173` |
| `GOOGLE_CLIENT_ID` | — | For Google OAuth sign-in |
| `EMAIL_HOST` | — | SMTP host (e.g. `smtp.gmail.com`) |
| `EMAIL_PORT` | — | e.g. `587` |
| `EMAIL_SECURE` | — | `true` for port 465, `false` for STARTTLS |
| `EMAIL_USER` | — | Sender address |
| `EMAIL_PASS` | — | App password |
| `CLOUDINARY_CLOUD_NAME` | — | Cloudinary cloud name |
| `CLOUDINARY_API_KEY` | — | Cloudinary API key |
| `CLOUDINARY_API_SECRET` | — | Cloudinary API secret |
| `GEMINI_API_KEY` | — | Google Generative AI key |

`MONGO_URI` and `JWT_SECRET` are the only hard requirements — the server won't start without them. Everything else degrades gracefully if missing.

### `frontend/.env`

| Variable | Description |
|----------|-------------|
| `VITE_API_URL` | Backend API base URL — defaults to `http://localhost:5000/api` |
| `VITE_SOCKET_URL` | Socket.IO server URL — defaults to `http://localhost:5000` |
| `VITE_GOOGLE_CLIENT_ID` | Google OAuth client ID |

## Security

- **Rate limiting** — 15 requests / 15 min on all auth endpoints to block brute force
- **Helmet** — sets security headers on every response
- **NoSQL injection prevention** — `express-mongo-sanitize` on all inputs
- **Passwords** — bcrypt hashed (12 rounds), never stored plain
- **OTP** — hashed before storage, 10-min expiry, 5-attempt lockout
- **Password reset tokens** — only the SHA-256 hash is stored; the plain token exists only in the email
- **File uploads** — restricted to images, video, audio, and PDF; 10 MB limit per file
