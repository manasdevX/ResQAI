ResQAI is a full-stack emergency management platform that coordinates disaster response across three roles — citizens, field responders, and admins — through a single, shared real-time interface.

When a disaster strikes, everyone needs different things. Citizens need to get help fast. Responders need to know where to go. Admins need to see everything at once. ResQAI gives each of them exactly that, all connected through live WebSocket events so nothing requires a page refresh.

## User Roles

| Role | Gets access to |
|------|----------------|
| **Citizen** | SOS button, incident reporting, shelter finder with check-in, resource requests, nearby incident feed, weather widget |
| **Responder (Volunteer)** | Incident dispatch feed, assignment management, resource fulfilment, skill profile, duty toggle |
| **Admin** | Everything above, plus analytics, user management, emergency broadcast alerts, shelter management, and the invite system |

**How roles are created:**
- **Citizens** and **Responders** select their role during standard signup.
- **Admins** are onboarded via a one-time invite link generated by an existing admin. Admin accounts can also be bootstrapped via the seed script.

## Features

### Authentication & Onboarding

**Two-step Email Signup (OTP)**  
Registration is a two-step process. The user fills in their name, email, optional phone number, and a strong password (validated in real-time with a 5-criteria strength meter), then chooses whether they are a citizen or a responder. On submission, a 6-digit OTP is emailed to them — the email itself never blocks the response. They enter the code on the next screen (with a 10-minute expiry and a 5-attempt lockout) to complete registration. Resending is rate-limited to once per 60 seconds.

**Google OAuth with Role Picker**  
Users can also register or sign in with Google. For brand-new Google users, if no role has been pre-selected (e.g. via an invite link), the backend returns a `requiresRole` flag and the frontend shows a role-picker modal before the account is created. Returning Google users have their avatar synced automatically without touching their name.

**Invite-Based Admin Onboarding**  
Admins generate one-time invite links from the Invites panel. A link expires after 48 hours, can only be used once, and automatically assigns the `admin` role to whoever registers through it. Optionally, the link can be tied to a specific email address. An existing admin can copy the link to share it or enter an email to have it sent automatically.

**Forgot & Reset Password**  
Users who forget their password can request a reset link from the login page. The backend generates a cryptographically secure token, stores only its SHA-256 hash, and emails the raw token as part of a reset URL. The link expires after 1 hour. To prevent email enumeration, the API always returns the same success response regardless of whether the email is found.

**Email Verification on Login**  
Accounts that went through the OTP signup flow but never verified their email are blocked at login and redirected to the OTP verification step.

### For Citizens

**SOS Emergency Alert**  
The SOS button is the most prominent control on the citizen home screen. A confirmation step guards against accidental triggers. On confirmation, the device's GPS coordinates are captured and an emergency incident is created with `critical` severity and the `isSOS` flag set. Every connected responder and admin receives a `sosAlert` socket event instantly. When a responder accepts the task, the original citizen gets a `sosAcknowledged` notification telling them who is coming.

**Incident Reporting**  
Citizens can report any emergency — fire, flood, earthquake, cyclone, landslide, accident, medical emergency, building collapse, chemical spill, riot, or other — with a title, description, GPS-pinned location, an affected people count, tags, and up to 5 photos, videos, or documents (10 MB each, stored on Cloudinary). The moment a report is submitted, it appears on the admin live map and in every responder's feed. The citizen can track their report's status (reported → acknowledged → responding → resolved) and receives a notification at each step. Duplicate detection prevents the same user from reporting the same incident type at the same spot within 30 minutes.

**AI Triage (Async)**  
Every incident submitted is automatically triaged by Gemini AI in the background after the HTTP response is sent, so the user never waits. The AI produces a severity rating, a 0–100 risk score, an estimated affected count, a plain-language summary, and a list of recommended actions. The result is pushed to all connected clients via a `incidentUpdated` socket event the moment it completes. If the primary model is unavailable, the system falls back to an alternative Gemini model automatically.

**Weather Widget**  
The citizen home screen includes a local weather widget. It uses the device's geolocation to fetch current conditions from the backend's weather proxy (which calls the Open-Meteo API — no API key required). It shows temperature, wind speed, a WMO weather code icon, day/night status, and an adverse-weather warning banner for severe conditions.

**Nearby Incident Feed**  
The home screen shows a live feed of active incidents near the user's location. Each card includes the incident type, severity badge, distance, and — once AI triage is complete — the first recommended action.

**Shelter Finder with Check-In**  
The Shelters page shows a Leaflet map alongside a searchable, filterable list of registered shelters. Citizens can filter by type (hospital, relief camp, school, community hall, government building), status (active, full, preparing, closed), and amenities (food, water, medical, electricity, WiFi, bedding, child care, wheelchair access). They can check themselves into a shelter directly from the app. The check-in is atomic — two concurrent requests cannot both fill the last available spot. Occupancy updates live for everyone via the `shelterOccupancyUpdated` socket event. A citizen can only be checked in to one shelter at a time; checking in elsewhere prompts them to check out first.

**Nearby Places (OpenStreetMap)**  
A second tab on the Shelters page pulls real hospitals, pharmacies, police stations, and fire stations from the OpenStreetMap Overpass API — no API key needed. The backend tries three Overpass mirrors in sequence and returns the closest results with distance in km.

**Resource Requests**  
Citizens can request food, water, medical help, clothing, or shelter from the home screen. Each request is pinned to their GPS location so nearby responders can see and fulfil it.

**Mark Yourself Safe**  
After an emergency, citizens can toggle their `isSafe` status from the home screen. This is also automatically set to `false` when an SOS is triggered, surfacing the "Mark Safe" control until they confirm they're okay.

### For Responders (Volunteers)

**Smart Dispatch Notifications**  
When a new incident is reported, the system immediately matches it against available responders based on their registered skill keywords. A fire goes to people with firefighting or rescue skills; a medical emergency goes to those with first aid, paramedic, or nursing skills, and so on. Matched responders get a `newIncidentAssigned` notification on their dashboard. If no skill-matched responders are available, the dispatch falls back to all available responders.

**Auto-Escalation**  
If no responder accepts an incident within 15 minutes, all active admins automatically receive an `incidentEscalated` socket notification so they can intervene with a manual assignment.

**Incident Feed & Acceptance**  
Responders have a dedicated incidents view showing active incidents — filterable by type and severity. They can view the full AI triage output and accept a task with one click. Accepting uses an atomic database update to prevent duplicate assignments.

**My Assignments**  
A separate page lists all incidents the responder is currently assigned to, with status and the ability to update progress.

**Resource Fulfilment**  
Responders see pending resource requests from citizens. They can acknowledge a request to claim it, then mark it fulfilled when it has been delivered.

**Skill Profile & Duty Toggle**  
Responders manage a free-text skills list from their dashboard (e.g. "first aid", "search and rescue", "driving"). They also have an ON DUTY / OFF DUTY toggle — going on duty makes them available for dispatch and updates the admin's live count immediately via socket.

### For Admins

**Live Incident Map**  
The admin dashboard is a full-screen split view: a live Leaflet map on one side showing every active incident as a colour-coded marker (red for critical, orange for high, yellow for medium, green for low), and a real-time incident feed on the other. New incidents appear on both the moment they are submitted. The feed also surfaces SOS alerts in a dedicated strip and escalation banners for incidents that haven't been accepted within 15 minutes.

**Incident Management**  
Clicking any incident opens a management panel where admins can change the status (reported → acknowledged → responding → resolved → closed → false_alarm), change severity, manually assign or unassign specific responders (with a notification sent to the assigned responder), and view the full status history log, attached media, and AI triage output.

**Emergency Broadcast**  
Admins can push a system-wide alert — evacuation, medical, shelter, or general — from the Alerts panel. It fires to every connected user via the `alertBroadcast` socket event instantly and is persisted to every user's notification inbox so offline users see it on their next login.

**Shelter Management**  
Admins can create, edit, and delete shelters; set capacity, type, description, amenities, and contact details; manually update occupancy (with absolute or delta values); and change status. All changes are broadcast via socket so the Shelters page stays in sync for all users in real time.

**Analytics Dashboard**  
A comprehensive data overview: total incidents, active and critical counts, resolution rate, average resolution time, SOS count, incident breakdown by severity / type / status, a 7-day daily trend bar chart, shelter utilisation rate and capacity, and responder on-duty vs. registered count. All driven by a single MongoDB aggregation endpoint.

**User Management**  
Admins can search and filter all registered users, view their details, change roles, and activate or deactivate accounts.

**Invite System**  
To onboard a new admin, generate a one-time invite link from the Invites panel. The link expires after 48 hours and can only be used once. Optionally, target it to a specific email address — the link is then emailed to that address automatically. The Invites panel shows all invite links with their status (active, used, expired), creation date, and expiry.

### Shared Features

**Real-Time Direct Messaging (Chat)**  
All roles can send direct messages to any other user. The chat includes:
- **Live presence** — green/grey dots show who is online right now
- **Typing indicators** — animated dots appear when the other person is typing
- **Unread badges** — per-conversation unread counts on the sidebar, cleared on open
- **Reply threads** — reply to a specific message with a quoted preview
- **Optimistic sending** — messages appear immediately with a "Sending…" state and are replaced by the server-confirmed message or marked as failed if delivery fails
- Persistent history scrollable on demand

**Notification Bell**  
Every user has a notification inbox in the top bar (bell icon) that surfaces in-app notifications: incident status changes, SOS acknowledgements, responder assignments, and system-wide emergency alerts. Unread count badge updates in real time via socket. Notifications are persisted in MongoDB so they survive page reloads.

**Profile Management**  
All users can update their display name, phone number, and avatar (uploaded to Cloudinary; max 2 MB image). The email address is read-only. Users can also change their password from the profile page with current-password verification and a strength meter for the new password. Google-signed-in users can change their password to set a standalone password.

## Getting Started

### Prerequisites

- Node.js v18+
- MongoDB (local or [Atlas](https://www.mongodb.com/atlas))
- [Cloudinary](https://cloudinary.com) account — for photo, video, and avatar uploads
- [Google AI Studio](https://aistudio.google.com) API key — for incident triage (Gemini)
- Google OAuth Client ID — for Google Sign-In / Sign-Up
- SMTP credentials — Gmail with an [App Password](https://support.google.com/accounts/answer/185833) works fine

### Setup

```bash
# Clone
git clone https://github.com/your-username/ResQAI.git
cd ResQAI

# Backend
cd backend
npm install
cp .env.example .env    # fill in your values (see table below)
npm run dev             # starts on http://localhost:5000

# Frontend (new terminal)
cd ../frontend
npm install
# create frontend/.env with your VITE_* variables
npm run dev             # starts on http://localhost:5173
```

### Create the first admin account

```bash
# from backend/
node seeds/createAdmin.js
```

The script prints the login credentials. Use them to log in and head to the **Invites** panel to onboard additional admins. Citizens and responders can self-register at `/signup`.

## Environment Variables

### `backend/.env`

| Variable | Required | Description |
|----------|:--------:|-------------|
| `MONGO_URI` | ✅ | MongoDB connection string |
| `JWT_SECRET` | ✅ | Signing secret — minimum 32 characters |
| `PORT` | — | HTTP port, defaults to `5000` |
| `FRONTEND_URL` | — | CORS origin and email link base — defaults to `http://localhost:5173`. Comma-separate multiple origins for production. |
| `GOOGLE_CLIENT_ID` | — | Google OAuth client ID (required for Google Sign-In) |
| `EMAIL_HOST` | — | SMTP host (e.g. `smtp.gmail.com`) |
| `EMAIL_PORT` | — | e.g. `587` |
| `EMAIL_SECURE` | — | `true` for port 465 (SSL), `false` for STARTTLS |
| `EMAIL_USER` | — | Sender email address |
| `EMAIL_PASS` | — | SMTP password or app-specific password |
| `CLOUDINARY_CLOUD_NAME` | — | Cloudinary cloud name |
| `CLOUDINARY_API_KEY` | — | Cloudinary API key |
| `CLOUDINARY_API_SECRET` | — | Cloudinary API secret |
| `GEMINI_API_KEY` | — | Google Generative AI key (for AI triage) |

`MONGO_URI` and `JWT_SECRET` are the only hard requirements — the server will not start without them. Email, Cloudinary, and Gemini features degrade gracefully if their keys are absent.

### `frontend/.env`

| Variable | Description |
|----------|-------------|
| `VITE_API_URL` | Backend API base URL — defaults to `http://localhost:5000/api` |
| `VITE_SOCKET_URL` | Socket.IO server URL — defaults to `http://localhost:5000` |
| `VITE_GOOGLE_CLIENT_ID` | Google OAuth client ID (required for Google Sign-In on the frontend) |

## Security

- **Rate limiting** — 15 requests per 15 minutes on all auth endpoints to block brute force attacks
- **Helmet** — sets recommended security headers (`X-Frame-Options`, `Content-Security-Policy`, etc.) on every response
- **NoSQL injection prevention** — `express-mongo-sanitize` strips `$` operators from all request body, query, and params inputs
- **Passwords** — bcrypt hashed at 12 rounds; plain text is never stored or logged
- **OTP** — bcrypt hashed before storage; 10-minute expiry; 5-attempt lockout per code; 60-second resend rate limit
- **Password reset tokens** — only the SHA-256 hash is stored; the raw token exists only in the one-time email; tokens expire after 1 hour
- **Email enumeration protection** — the `/forgot-password` endpoint always returns the same success response regardless of whether the email is registered
- **File upload restrictions** — only images, video, audio, and PDF are accepted; 10 MB per file; 5 files per incident; avatar uploads limited to 2 MB images
- **Role-based data isolation** — citizens can only query their own incidents; responders can filter to their own assignments; admin-only routes are middleware-guarded
- **Atomic operations** — shelter check-in and incident acceptance use MongoDB `findOneAndUpdate` with filter conditions to prevent race conditions on concurrent requests
- **Invite-only admin creation** — the `admin` role cannot be self-selected at signup; it is only granted through a time-limited, single-use invite token
